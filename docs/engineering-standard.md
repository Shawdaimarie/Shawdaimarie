## Working standard

- Inspect existing code, conventions, instructions, and checks before editing.
- Implement the agreed user outcome with explicit scope and acceptance criteria.
- Prefer the project's existing language and architecture; do not introduce a
  language or framework merely to increase the language count.
- Preserve user changes and unrelated files. Keep edits small and reviewable.
- Use clear names, typed boundaries where appropriate, input validation, and
  least-privilege access. Keep secrets out of source, examples, and logs.
- For interfaces, use semantic structure, keyboard access, readable contrast,
  responsive layouts, and useful loading, error, and empty states.
- For AI features, document model and data dependencies, evaluation cases,
  failure behavior, human review boundaries, and usage costs.
- Run checks relevant to the changed behavior. Report the exact commands,
  outcomes, and checks not run. Never invent passing tests or benchmark results.
- Write concise setup, API, troubleshooting, and handoff documentation. Verify
  examples when possible and distinguish examples from measured outcomes.
- Keep profile claims consistent with README.md and linked evidence. No invented
  employers, degrees, certifications, clients, production adoption, or income.
- Do not provision paid resources, enable unattended spending, publish a site,
  or expose private data as a side effect of editor setup.


## Repository context

This repository contains a GitHub profile and writing samples. It is not an
eight-language application. Do not invent build commands or add unnecessary
runtimes. For Markdown-only changes, check links, spelling, claim consistency,
and rendering. Use each application's own existing checks when these settings
are adapted to another repository.

## Review before delivery

1. Confirm the user problem and acceptance criteria.
2. Review the diff for correctness, sensitive data, accessibility, and scope.
3. Run appropriate checks and retain their actual output.
4. Document setup, dependencies, limits, ownership, and relevant recovery steps.
5. Describe what changed, what was verified, and what remains unresolved.
6. Update affected public descriptions after meaningful releases, using measured
   evidence rather than unsupported adjectives.

## Design direction

Use restrained, legible presentation and a clear hierarchy. Public portfolio
materials may use white, pink, and gold accents, with accessible contrast.
Respect each product's established design system. Do not force brand colors
into editor syntax highlighting or client interfaces.

## Maintenance

Review standards when a project, claim, or supported tool changes. Files in Git
are versioned configuration, not a live cross-device sync service. Pull changes
in each working copy; merge these files with existing project rules rather than
overwriting them. No recurring job or automation is enabled by these files.
