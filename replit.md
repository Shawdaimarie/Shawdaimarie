## Project context

Preserve that purpose. Do not add a server, database, deployment, or eight language
runtimes just to demonstrate configuration. In another project, merge these
standards with its real architecture and existing run instructions.

## Working standard

- Read README.md and docs/engineering-standard.md before changing this workspace.
- Inspect existing code, conventions, instructions, and checks before editing.
- Implement the agreed user outcome with explicit scope and acceptance criteria.
- Prefer the project's existing language and architecture; do not introduce a
  language or framework merely to increase the language count.
- Preserve user changes and unrelated files. Keep edits small and reviewable.
- Use clear names, typed boundaries where appropriate, input validation, and
  least-privilege access. Keep secrets out of source, examples, and logs.
- For interfaces, use semantic structure, keyboard access, readable contrast,
  responsive layouts, and useful loading, error, and empty states.
- For AI features, document model and data dependencies, evaluation cases,
  failure behavior, human review boundaries, and usage costs.
- Run checks relevant to the changed behavior. Report the exact commands,
  outcomes, and checks not run. Never invent passing tests or benchmark results.
- Write concise setup, API, troubleshooting, and handoff documentation. Verify
  examples when possible and distinguish examples from measured outcomes.
- Keep profile claims consistent with README.md and linked evidence. No invented
  employers, degrees, certifications, clients, production adoption, or income.
- Do not provision paid resources, enable unattended spending, publish a site,
  or expose private data as a side effect of editor setup.
